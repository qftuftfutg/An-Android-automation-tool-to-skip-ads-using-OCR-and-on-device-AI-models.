# 第一部分 清屏：链路层问题（P0）

## P0-1 截图全链路失效

### 现象

所有识别日志都是同一句：

```
结果：系统截图为空或编码失败；没有运行视觉推理
```

系统桌面、好游快爆、酷狗、DSH，无一例外。OCR 一次都没跑起来，后续所有 OCR/AI 相关逻辑形同虚设。

### 排查过程（走过的两段弯路）

**弯路一：怀疑 colorSpace 为 null**

OEM 设备上 `ScreenshotResult.colorSpace` 可能返回 null，`wrapHardwareBuffer` 会因此抛异常。加了 sRGB 兜底：

```kotlin
val space = runCatching { screenshot.colorSpace }.getOrNull()
    ?: ColorSpace.get(ColorSpace.Named.SRGB)
```

**结果：无效**，日志仍然是「编码失败」。

**弯路二：怀疑显示器 ID 不对**

加了 `resolveCaptureDisplayId()`，从 DisplayManager 查默认显示器：

```kotlin
takeScreenshot(resolveCaptureDisplayId(), aiScreenshotExecutor, callback)
```

**结果：无效**。

**教训**：这两次都是在没有证据的情况下改代码。真正解决靠的是第三步——加诊断日志。

### 诊断日志带来的关键证据

在 `encodeEphemeralScreenshot` 里加了一个 `encodeFailureDetail` 字段，逐步骤赋值：

```kotlin
encodeFailureDetail = "未开始编码"
val declaredSpace = runCatching { screenshot.colorSpace }.getOrNull()
val bufferInfo = runCatching {
    "format=${hardwareBuffer.format} size=${hardwareBuffer.width}x${hardwareBuffer.height} layers=${hardwareBuffer.layers}"
}.getOrElse { "bufferInfo 不可读(${it.javaClass.simpleName})" }

val wrapped = runCatching { Bitmap.wrapHardwareBuffer(hardwareBuffer, space) }
val source = wrapped.getOrNull()
if (source == null) {
    encodeFailureDetail = "wrapHardwareBuffer 失败：$bufferInfo；" +
        "colorSpace=${if (declaredSpace == null) "null→SRGB兜底" else declaredSpace.name}；" +
        (err?.let { "${it.javaClass.simpleName}：${it.message?.take(40) ?: "无消息"}" } ?: "返回null且无异常")
    return null
}
```

调用方把原因拼进日志：

```kotlin
val encoded = try { encodeEphemeralScreenshot(screenshot) } catch (e: Exception) {
    encodeFailureDetail = "异常 ${e.javaClass.simpleName}：${e.message?.take(60) ?: "无消息"}"
    null
}
if (encoded == null) {
    val reason = "系统截图为空或编码失败（$encodeFailureDetail）；没有运行视觉推理"
```

下一次开屏，日志立刻给出真凶：

```
系统截图为空或编码失败（异常 IllegalArgumentException：Software rendering doesn't support hardware bitmaps）
```

### 根因

`Bitmap.wrapHardwareBuffer()` 返回的是 **HARDWARE config** 的位图——像素住在 GPU 显存里。原代码用软件 Canvas 去绘制它：

```kotlin
val source = Bitmap.wrapHardwareBuffer(hardwareBuffer, space)   // HARDWARE config
val compact = Bitmap.createBitmap(width, height, ARGB_8888)     // 软件位图
Canvas(compact).drawBitmap(source, null, rect, paint)           // ← 抛异常
```

Android 明确禁止软件 Canvas 绘制硬件位图。异常被外层 `try { encodeEphemeralScreenshot(...) } catch (_: Exception) { null }` 吞掉，最终只表现为「编码失败」四个字。

### 修复

```kotlin
// wrapHardwareBuffer 返回 HARDWARE config，软件 Canvas 无法绘制它
// （IllegalArgumentException: Software rendering doesn't support hardware bitmaps）。
// 先把它拷贝成普通内存位图，之后才能缩放和 JPEG 编码。
val software = runCatching { source.copy(Bitmap.Config.ARGB_8888, false) }.getOrNull()
if (software == null) {
    encodeFailureDetail = "hardware bitmap 拷贝到 ARGB_8888 失败；$bufferInfo → ${width}x${height}"
    return null
}
val compact = Bitmap.createScaledBitmap(software, width, height, true)
```

`copy()` 把 GPU 显存里的像素拷一份到普通内存，之后软件 Canvas 就能处理了。

### 代价与安全

全屏位图拷贝，1080×2400 ARGB_8888 约 **10 MB** 瞬时内存。但并发被 `aiCapturesInFlight` 限制为 1：

```kotlin
val blockedByThrottle = aiCapturesInFlight.isNotEmpty() || ...
```

编码完立即 recycle，峰值约 11 MB、持续几十毫秒。

### 验证

```
修复前：系统截图为空或编码失败；没有运行视觉推理
修复后：OCR 完成 · 文本块=15；文本行=15；耗时=253ms
       酷狗 · AccessibilityNodeInfo.ACTION_CLICK · 系统接受了点击操作
```

## P0-2 OCR 分辨率太低，认不出「跳过」

### 现象

截图修好后 OCR 能跑了，但所有应用都是：

```
通过安全短标签的行=0；疑似跳过（仅诊断）=无（共 0 行）
```

OCR 明明识别出 9~12 块文字，却连一个「跳」字都没看到。而同一时刻无障碍节点读到的是 `text=跳过`。

### 根因

缩放系数硬编码 512：

```kotlin
val scale = minOf(512f / source.width, 512f / source.height, 1f)
```

屏幕 1080×2400 缩到 512×1138，缩小到 **47%**。开屏右上角的「跳过」按钮通常 100×50 px，缩放后只剩 **约 47×24 像素**。中文两个字挤在 24 像素高度里，OCR 抓不住。

### 为什么一直没发现

因为 OCR 的「文本块=10」看起来很正常——大标题能认，小按钮认不出。**数量对得上，质量对不上。**

### 修复（分两步）

**第一步**：硬编码提到 1280。

**第二步**：按用户要求做成界面可调，四档：

```
○ 720p ：最快，小号「跳过」可能识别不到
○ 1080p：推荐（默认）
○ 1440p：更清晰，耗时略增
○ 2160p：最清晰，最慢
```

存储键 `screenshot_long_edge_v1`，读取时做范围钳制：

```kotlin
private fun screenshotLongEdgePx(): Float =
    prefs.getInt(
        MainActivity.PREF_SCREENSHOT_LONG_EDGE,
        MainActivity.DEFAULT_SCREENSHOT_LONG_EDGE      // 1080
    ).coerceIn(480, 2400).toFloat()
```

越界值自动回落到合法区间，不会因为存储被改坏而崩溃。

### 为什么不需要给 AI 单独准备低分辨率

用户曾提议做双份编码（OCR 用高分辨率、AI 用低分辨率）。实际不需要——AI 推理入口无条件缩到 224：

```kotlin
private fun letterbox(source: Bitmap): Bitmap {
    val output = Bitmap.createBitmap(INPUT_SIZE, INPUT_SIZE, ...)   // INPUT_SIZE = 224
    canvas.drawColor(Color.rgb(114, 114, 114))
    ...
}
```

送进去 512 还是 1280，最终都是 224×224。**高分辨率对 AI 零收益，只多花解码时间；一份高分辨率同时满足两者。**

### 验证

```
21:27:09  通过安全短标签的行=1；疑似跳过="跳过4"[0.833,0.061,0.916,0.075]
21:37:07  通过安全短标签的行=1；疑似跳过="免广告跳过"[0.633,0.066,0.918,0.089]
```

诊断行带归一化坐标，可直接和控件框比对。

## P0-3 倒计时导致 OCR 证据永远失效

### 现象

好游快爆的跳过按钮带倒计时（`跳过 5` → `跳过 4` → `跳过 3`），日志表现为无限循环：

```
21:34:03  OCR 安全规则核对  判定门=①OCR证据  OCR 缓存=无  → DEFER
21:34:04  OCR 完成  "跳过5" 通过安全短标签=1
21:34:04  通用跳过规则  命中证据：跳过 4  → 等待 OCR 证据
21:34:05  通用跳过规则  命中证据：跳过 3  → 等待 OCR 证据
21:34:06  通用跳过规则  命中证据：跳过 2  → 等待 OCR 证据
```

OCR 明明成功写入了缓存，下一次检查却还是「无」。

### 根因链

**1. 签名包含所有文本**

```kotlin
private fun computeScreenSignature(nodes: List<AccessibilityNodeInfo>): String {
    val digest = MessageDigest.getInstance("SHA-256")
    nodes.forEachIndexed { index, node ->
        val fields = listOf(
            index.toString(), node.packageName?.toString().orEmpty(), node.className?.toString().orEmpty(),
            node.viewIdResourceName.orEmpty().take(160),
            node.text?.toString().orEmpty().take(96),          // ← 倒计时文本参与哈希
            node.contentDescription?.toString().orEmpty().take(96),
            "${node.isVisibleToUser}:${node.isEnabled}:${node.isClickable}:..."
        )
        fields.forEach { field ->
            digest.update(field.toByteArray(Charsets.UTF_8))
            digest.update(0.toByte())
        }
    }
    ...
}
```

**2. 倒计时每秒改 text → 签名每秒变化**

**3. 第①门要求签名完全相等**

```kotlin
ocrSceneCache[pkg]?.takeIf {
    it.sessionStartedAt == sessionStart && it.screenSignature == currentScreenSignatures[pkg] &&
        now - it.sourceCaptureAt in 0..AI_RESULT_MAX_AGE_MS
}
```

**4. 缓存刚写入就判为失效 → 永远 DEFER**

### 第一次修复尝试（不够）

在签名前归一化倒计时数字：

```kotlin
private fun normalizeForSignature(raw: String): String {
    if (raw.isEmpty()) return raw
    var value = raw
    value = value.replace(
        Regex("(?i)(跳过|skip)\\s*\\d{1,2}\\s*(秒|s|sec(?:onds)?)?"), "$1#"
    )
    value = value.replace(Regex("^\\d{1,3}$"), "#")
    value = value.replace(Regex("\\d{1,2}\\s*秒"), "#秒")
    return value
}
```

**这个修复没有彻底解决问题**。日志显示好游快爆仍然一直 DEFER，而且出现：

```
AI 高危否决 · 结果：屏幕签名或前台会话变化；丢弃过期 OCR/AI 结果
```

说明还有其它字段在变（父容器文本、兄弟节点的倒计时进度、或未覆盖的形态）。

### 最终修复：去掉签名相等要求

```kotlin
// 第①门不再要求屏幕签名完全一致：倒计时按钮每秒改写自身文本，签名会持续变化，
// 若强制相等，OCR 证据永远拿不到（实测好游快爆因此一直 DEFER）。
// 同一开屏会话 + 未超出有效期已足够；会话变化由 sessionStart 保证。
val cached = synchronized(aiLock) {
    ocrSceneCache[pkg]?.takeIf {
        it.sessionStartedAt == sessionStart &&
            now - it.sourceCaptureAt in 0..AI_RESULT_MAX_AGE_MS
    }
}
```

只保留两道约束：**同一开屏会话** + **未超有效期**。

诊断日志里保留观察字段：

```
签名是否一致=${rawCached != null && rawCached.screenSignature == currentScreenSignatures[pkg]}
```

### 权衡

页面跳转后可能仍用旧 OCR。但有 `foregroundSessionStartedAt` 兜底（前台会话变化会重置 sessionStart），且开屏窗口本身只有 10 秒。

`normalizeForSignature()` 保留，它仍在为 AI 缓存（`aiSceneCache`）服务。

## P0-4 文字节点不可点击

### 现象

好游快爆走到第②门，卡在最后一项：

```
判定门=②原生目标
控件自身安全短标签=[跳过 3]
可见=true；启用=true；可点=false     ← 这一项
bounds有效=true；小控件=true
bounds=(1151,160,1376,269)；屏幕=1440x3168
```

### 根因

`findAndClickSkipTarget()` 里有一句明确的注释，禁止向上找父节点：

```kotlin
private fun findAndClickSkipTarget(target: AccessibilityNodeInfo): Boolean {
    val labels = listOf(...)
    if (labels.none { isSafeSkipControlLabel(it) }) return false
    if (!target.isVisibleToUser || !target.isEnabled || !target.isClickable) return false
    if (!hasValidCandidateBounds(target) || !isSplashCandidateRegion(target)) return false
    // Deliberately no parent walk and no coordinate-gesture fallback for splash-skip targets.
    return target.performAction(AccessibilityNodeInfo.ACTION_CLICK)
}
```

好游快爆的 `com.xmcy.hykb:id/skip` 是纯文字节点，`isClickable=false`，真正 setOnClickListener 的是外层容器。这条路径永远失败。

**这个限制源自 1.3.0**：当时为了修「抖音搜索结果被误点」，明确取消了父节点升级（见第五部分 H-1）。

### 修复

新增向上取可点祖先的函数，但**严格限制父容器尺寸**：

```kotlin
private fun resolveClickableTarget(target: AccessibilityNodeInfo, maxUp: Int = 2): AccessibilityNodeInfo? {
    if (target.isClickable) return target
    var current = target
    var depth = 0
    while (depth < maxUp) {
        val parent = current.parent ?: return null
        if (parent.isClickable && ancestorFitsTarget(parent, target)) return parent
        if (current !== target) current.recycle()
        current = parent
        depth++
    }
    if (current !== target) current.recycle()
    return null
}

private fun ancestorFitsTarget(ancestor: AccessibilityNodeInfo, target: AccessibilityNodeInfo): Boolean {
    val ab = Rect(); val tb = Rect()
    ancestor.getBoundsInScreen(ab)
    target.getBoundsInScreen(tb)
    if (ab.width() <= 0 || ab.height() <= 0) return false
    if (!ab.contains(tb)) return false
    val aArea = ab.width().toLong() * ab.height().toLong()
    val tArea = (tb.width().toLong() * tb.height().toLong()).coerceAtLeast(1L)
    return aArea <= tArea * 4L && ab.width() <= tb.width() * 3 && ab.height() <= tb.height() * 3
}
```

同时改两处：
- `findAndClickSkipTarget`：用解析出的节点执行点击，用完 recycle
- 第②门的 `clickable`：改成 `resolveClickableTarget(target) != null`

### 尺寸限制的意义

父容器面积不能超过目标 4 倍、宽高不能超过 3 倍。按钮的紧邻容器能通过，整屏 ViewGroup 通不过。

**仍然不做坐标手势兜底**——那会绕过所有安全检查。

## P0-5 跳过按钮被限制必须在右上角

### 现象

用户原话：「有的时候跳过键可能是在任意的一个角落」。

### 根因

```kotlin
private fun isTopRightSplashRegion(node: AccessibilityNodeInfo): Boolean {
    return bounds.centerX() >= width * 0.55f &&           // 必须在中线右侧
        bounds.right <= width * 1.02f &&
        bounds.top >= 0 && bounds.top <= height * 0.35f &&   // 必须在上部 35%
        bounds.width() <= width * 0.45f &&
        bounds.height() <= height * 0.18f &&
        area <= screenArea * 8L / 100L
}
```

判定矩阵：

| 位置 | 结果 | 原因 |
|---|---|---|
| 右上角 | ✅ | — |
| 右下角 | ❌ | top 超 35% |
| 左下角 | ❌ | centerX 不够 |
| 左上角 | ❌ | centerX 不够 |
| 正下方 | ❌ | 两者都不满足 |

这个函数被 **7 处**引用，是核心安全门。**即使 OCR 认出「跳过」、文案完全一致、位置也重合，只要不在右上就 VETO。**

### 修复

函数改名 `isSplashCandidateRegion`，**去掉全部位置约束，只保留尺寸包络**：

```kotlin
/**
 * 开屏跳过控件必须是「小控件」，但**不再限制位置**。
 *
 * 早期的实现在这里硬性要求右上角（centerX ≥ 55%、top ≤ 35%），但真实开屏广告把
 * 「跳过 / Skip / ×」放在左上、左下、右下、正下方甚至中右都很常见，于是 OCR 明明
 * 识别成功、文案也完全一致，仍然在原生检查这一关被拒。
 *
 * 现在只保留尺寸包络：任何位置的小控件都可以成为候选。位置一致性由后续的第④门
 * （OCR 文案与控件位置重合 ≥ OCR_POSITION_MIN_OVERLAP）继续把关。
 */
private fun isSplashCandidateRegion(node: AccessibilityNodeInfo): Boolean {
    val bounds = Rect()
    node.getBoundsInScreen(bounds)
    val width = resources.displayMetrics.widthPixels
    val height = resources.displayMetrics.heightPixels
    if (bounds.width() <= 0 || bounds.height() <= 0 || width <= 0 || height <= 0) return false
    val area = bounds.width().toLong() * bounds.height().toLong()
    val screenArea = width.toLong() * height.toLong()
    return bounds.width() <= width * 0.45f &&
        bounds.height() <= height * 0.18f &&
        area > 0 && area <= screenArea * 8L / 100L
}
```

连带更新 7 处引用与文案：

| 位置 | 改动 |
|---|---|
| 日志字段 | `右上区域=true` → `小控件=true` |
| 三个包名规则名 | `（包名 + 短标签 + 右上区域）` → `（包名 + 短标签 + 小控件）` |
| 拒绝原因 | `不在开屏右上区域` → `尺寸或 bounds 不满足小控件约束` |
| 提示文案 | `开屏广告右上角按钮` → `开屏广告的关闭按钮` |

### 注意

好游快爆的按钮本身就在右上（`[0.833,0.061,0.916,0.075]`），所以这个修复对它没用——它卡的是 P0-4。位置放宽是为其它应用准备的。

# 第二部分 清屏：匹配层问题（P1）

## P1-1 规则导入计数误报 1119 条

### 现象

导入 `李跳跳2088条规则.txt` 后对话框显示：

```
可识别弹窗规则：2404 条
超出上限或格式无效的条目：1119 条
```

看起来像丢了一大半规则。

### 实际分析

用 Node 脚本解析原文件（226,345 字节）：

```
条目总数            2088
├── 含 popup_rules   985 个配置
│   └── 规则总数     2383 条（全部有效：id 是字符串且 action 非空）
├── 只有开关字段     1077 个（如 {"ltt_service": true}，压根没有规则）
├── JSON 格式错        14 个（尾逗号）
└── 值不是字符串       10 个
```

单应用规则数全部 ≤ 100，`MAX_RULES_PER_APP = 100` **根本不是原因**（一度怀疑是它）。

### 根因（两个独立 bug）

**bug 1：空配置被算成无效**

```kotlin
if (!consumed) ignored++      // 只有服务开关、没有规则的配置也被计数
```

**bug 2：JSON 解析失败被计了两次**

```kotlin
is String -> try { parseConfigLenient(raw) } catch (_: Exception) { ignored++; null }
...
if (config == null) { ignored++; continue }    // 又加一次
```

### 修复

- `ImportedRuleSet` 删除 `ignoredEntries` 字段（无用且误导）
- `RuleImportResult` 拆成两个计数：
  - `failedEntries` —— 真格式无效（JSON 错、值非字符串、规则字段为空）
  - `skippedNoRule` —— 空配置（只含开关）
  - 另加 `importedEntries` 计算属性
- 主循环用 `itemFailed` 标记区分两类，去掉重复计数

### 验证

```
旧版：超出上限或格式无效：1119
```

## P1-2 `=跳过` 精确匹配打不中倒计时

### 背景

用户问：「这个文件里面有很明确的跳转规则，为啥不用啊」

### 分析：规则库的真实构成

2404 条规则统计：

```
条件(id)含「跳过/skip」      只有 18 条
动作(action)含「跳过/skip」  只有 48 条
其余 2300+ 条                全是弹窗关闭类
```

id 形态分布：

```
中文文本（如「开启青少年模式」）  1374 条
viewId（下划线英文标识）          822 条
其它                              208 条
```

抽样：

| 应用 | 规则内容 |
|---|---|
| 酷狗 | `开启青少年模式 → 知道了` |
| 快手 | `reminder_push_guide_tv → …close`、`你可能感兴趣的人 → 关闭` |
| 抖音 | `检测到更新 → 以后再说`、`青少年模式 → 关闭`、`朋友推荐 → close` |

**这份规则库主要解决「烦人弹窗」，开屏广告跳过只有十几条。**

### 应用标识匹配是正确的

文件里的数字键是应用包名的 Java `String.hashCode()`：

```
com.kugou.android.lite      hashCode=-1491765371   在文件里=是
com.sankuai.meituan         hashCode=-1709882794   在文件里=是
com.smile.gifmaker          hashCode=1659293491    在文件里=是
com.ss.android.ugc.aweme    hashCode=313184810     在文件里=是
com.xmcy.hykb（好游快爆）   hashCode=-562730018    在文件里=否
com.tencent.tmgp.dfm（CF）  hashCode=-1950564683   在文件里=否
```

好游快爆和 CF 手游**不在规则库里**。

### 真正的 bug

规则库里最常见的跳过写法是：

```json
{"id":"=跳过","action":"=跳过"}
```

`=` 是李跳跳的精确匹配语法：

```kotlin
'=' -> hay == needle        // text 必须正好等于「跳过」
```

但开屏按钮实际文本是 **`跳过 5`**（带倒计时）。`"跳过 5" == "跳过"` 为假，规则全部失效。

### 修复

```kotlin
// 「=跳过」在规则库里是最常见的精确写法，但开屏按钮的实际文本
// 常带倒计时（「跳过 5」「跳过3秒」），严格相等会全部错过。
// 这里只对跳过类文案容忍倒计时数字，其它 '=' 仍保持严格语义。
'=' -> hay == needle ||
    (needle == "跳过" || needle == "skip") &&
    isGenericCountdownSkipLabel(candidate)
```

## P1-3 `免广告 跳过` 的空格打不中正则

### 现象

```
21:43:12  疑似跳过（仅诊断）="免广告 跳过"[0.639,0.065,0.902,0.087]（共 2 行）
21:43:13  判定门=③文案一致  控件自身安全短标签=[跳过]
          OCR 保留的短跳过标签=[]（共 0 行）      ← OCR 侧为空
```

OCR 明明认出了，却不进安全标签集合。

### 根因

OCR 把按钮拆成「免广告」和「跳过」两段，中间带空格。而：

```kotlin
private fun normalizeControlLabel(raw: String): String = raw
    .replace('　', ' ')
    .replace(Regex("\\s+"), " ")     // 多空格压成一个，但不去掉
    .trim()
    .lowercase(Locale.ROOT)
```

**只压缩、不删除**。所以 `"免广告 跳过"` 保留了中间空格，匹配不上 `explicitSkipRule` 正则里的 `免广告跳过`。

### 修复

只在 `explicitSkipRule` 里去空格，**不动 `normalizeControlLabel`**（它的压缩语义在别处还要用）：

```kotlin
private fun explicitSkipRule(rawLabel: String): String? {
    // OCR 常把按钮拆成「免广告 跳过」这种带空格的形式；normalizeControlLabel 只压缩空白，
    // 这里再去掉全部空白，让「免广告 跳过」与「免广告跳过」等价。
    val label = normalizeControlLabel(rawLabel).replace(" ", "")
    if (label.isBlank() || label.length > 32) return null
    ...
}
```

## P1-5 第③门「完全相等」过严

### 现象

控件标签是「跳过」，OCR 是「免广告跳过」，完全相等不成立。

### 修复

新增等价判断，从「相等」放宽到「包含」，但限制长度：

```kotlin
/**
 * 控件自身标签与 OCR 行是否指向同一个跳过按钮。
 *
 * 完全相等是最强的证据，但按钮渲染出来的文字常常比无障碍标签更长或更短：
 * 控件 label 是「跳过」，而按钮画的是「免广告跳过」；反过来也有。
 * 因此允许一方包含另一方，但两者都必须是不超过 12 字的短标签，
 * 避免「点击跳过验证」这类正文把按钮比出来。
 */
private fun skipLabelsAgree(nodeLabel: String, ocrLabel: String): Boolean {
    if (nodeLabel.isBlank() || ocrLabel.isBlank()) return false
    if (nodeLabel == ocrLabel) return true
    if (nodeLabel.length > 12 || ocrLabel.length > 12) return false
    return ocrLabel.contains(nodeLabel) || nodeLabel.contains(ocrLabel)
}
```

## P0-16 AI 不可用时绕过原生检查

### 现象

```kotlin

    return if (prefs.getBoolean(PREF_AI_TIMEOUT_FALLBACK, true)) ALLOW else VETO
}
```

因为模型永远装不上，`isFallback` 永远为 true，所以**安全输出模式下四道门一道都不走**。

### 一处需要纠正的误判

外部审查意见认为「ALLOW 等于授权点击」，这个说法不准确。`triggerClick` 后面还有两道独立关卡：

```kotlin
// 观察模式 / 自动点击开关
val autoSkipEnabled = prefs.getBoolean(MainActivity.PREF_AUTO_SKIP, false)
val observationOnly = prefs.getBoolean(MainActivity.PREF_OBSERVATION_MODE, true)
if (observationOnly || !autoSkipEnabled) {
    statsDb.logEvent(..., "观察模式：未执行点击", ...)
    return
}

// 屏幕签名复验
if (strictSkipTarget && !currentActiveWindowMatchesSignature(pkg)) {
    statsDb.logEvent(..., "stale_token_discard", "目标验证后屏幕签名变化；丢弃动作", ...)
    return
}
```

**观察模式确实保证零点击**（`observationOnly = true` 时 `autoEnabled` 恒为 false）。李跳跳规则路径同理：

```kotlin

val accepted = autoEnabled && aiAllowed && performGlobalAction(GLOBAL_ACTION_BACK)
```

### 真正的漏洞

短路同时跳过了 **第②门（原生目标安全检查）**，而那一门是完全不依赖 OCR 的纯原生检查。

真实语义是：

> 安全输出模式 + AI 不可用 = 只要控件文本匹配「跳过」且在开屏窗口内，原生目标检查也不做，直接进入点击流程。

### 修复

抽出独立函数，AI 回退分支与常规第②门**共用同一份判定**：

```kotlin
private class NativeTargetCheck(
    val passed: Boolean,
    val labels: List<String>,
    val bounds: Rect,
    val detail: String
)

/**
 * Native target check: the control itself must carry a safe short skip label and be visible,
 * enabled, clickable, with valid bounds inside the small-control envelope.
 *
 * Deliberately independent of OCR, AI availability and recognition mode. The AI-fallback
 * branch and the regular gate ② share this exact function so a model outage can never skip it.
 */
private fun nativeTargetCheck(target: AccessibilityNodeInfo): NativeTargetCheck {
    val labels = listOf(
        target.text?.toString().orEmpty().trim(),
        target.contentDescription?.toString().orEmpty().trim()
    ).filter { isSafeSkipControlLabel(it) }
    val bounds = Rect()
    target.getBoundsInScreen(bounds)
    val visible = target.isVisibleToUser
    val enabled = target.isEnabled
    val resolved = resolveClickableTarget(target)
    val clickable = resolved != null
    if (resolved != null && resolved !== target) resolved.recycle()
    val boundsOk = hasValidCandidateBounds(target)
    val smallControl = isSplashCandidateRegion(target)
    val passed = labels.isNotEmpty() && visible && enabled && clickable && boundsOk && smallControl
    val detail = "控件自身安全短标签=[${labels.joinToString(" | ")}]；" +
        "可见=$visible；启用=$enabled；可点=$clickable；bounds有效=$boundsOk；小控件=$smallControl；" +
        "bounds=(${bounds.left},${bounds.top},${bounds.right},${bounds.bottom})；" +
        "屏幕=${resources.displayMetrics.widthPixels}x${resources.displayMetrics.heightPixels}"
    return NativeTargetCheck(passed, labels, bounds, detail)
}
```

回退分支：

```kotlin
if (mode == RecognitionMode.SAFETY_OUTPUT && isFallback && !requireOcrWhenFallback) {
    val native = nativeTargetCheck(target)
    if (!native.passed) {
        logOcrCandidateDecision(pkg, now, "fallback-native-fail",
            "AI 不可用且候选未通过原生目标安全检查；拒绝该候选", ...)
        return CandidateGateDecision.VETO
    }
    val allowOnFallback = prefs.getBoolean(MainActivity.PREF_AI_TIMEOUT_FALLBACK, true)
    logOcrCandidateDecision(pkg, now, "fallback-native-pass", ...)
    return if (allowOnFallback) CandidateGateDecision.ALLOW else CandidateGateDecision.VETO
}
```

`NativeTargetCheck` 同时把 `labels` 和 `bounds` 交回，供第③④门复用，**避免重复读节点导致两次判定不一致**。

## P0-17 截图落盘的安全顾虑

### 用户原话

> 「那不保存到储存临时保存到内存里可以吗？」

### 原实现

### 新实现（`EphemeralAiImageStore.kt` 整体重写）

```kotlin
/**
 * In-memory holder for one-shot AI screenshots.
 *
 * 截图只在内存里存在：不写文件、不进相册/共享存储、不上传、不落统计库。
 * 压缩与缩放仍由调用方 encodeEphemeralScreenshot 负责，
 * 这里只负责持有那份字节并在关闭时清零。
 */
internal class EphemeralAiImageStore {

    fun stage(encodedImage: ByteArray): Lease {
        require(encodedImage.isNotEmpty()) { "截图内容为空" }
        check(encodedImage.size <= MAX_IMAGE_BYTES) { "截图超出单张内存上限" }
        return Lease(encodedImage.copyOf())
    }

    fun cleanupStaleFiles() = Unit      // 纯内存实现，没有文件残留

    internal class Lease internal constructor(private var payload: ByteArray?) : Closeable {
        fun readBytes(): ByteArray = (payload ?: error("临时图片已释放")).copyOf()
        override fun close() { payload?.fill(0); payload = null }
    }

    companion object { private const val MAX_IMAGE_BYTES = 1_500_000 }
}
```

**压缩设计完全未改**（512px/55%，后来改成可配），只把「落盘」换成「内存」。

## H-1（1.3.0）抖音搜索结果被误当成广告跳过按钮

### 问题

全局跳过识别会在长控件文字中搜索子字符串，文章标题提到「开屏广告跳过」也可能触发匹配；通用点击函数还会向上查找多个可点击父节点，存在点中搜索结果卡片的风险。

### 修复

- 仅将控件自身短文字 / contentDescription 的**完整字段**与明确广告跳过标签匹配；长文案、标题、正文关键词不能触发默认跳过
- 专属的「跳过 / Skip」倒计时只对应用商店、酷狗概念版、哔哩哔哩启用，并要求前台包名匹配及控件位于屏幕右上区域
- 严格广告按钮点击路径最多检查两层父节点，要求标签安全、父控件面积/尺寸与候选控件合理；**不会对非可点击正文节点做固定坐标兜底**
- 导入的广告跳过规则遇到长正文条件或长动作目标时拒绝执行并写日志
- 开屏广告跳过规则限于应用进入前台后的 10 秒窗口；锁屏 / 指纹验证状态下不自动点击
- 新增「正文误命中防护」「候选按钮位置防护」「规则窗口关闭」等日志原因

### 后遗症

这条修复引入了两个后来的问题：
1. **P0-4**：取消了父节点升级，导致文字节点永远点不到

# 第十三部分 经验教训

## 13.1 关于排查

1. **模糊的错误信息是最大的敌人**
   `系统截图为空或编码失败` 藏了一个具体的 `IllegalArgumentException`，害前面几轮都在猜。加上「把失败点写进日志」之后，一次命中。

2. **先让链路可证伪，再谈调优**
   截图 → 编码 → OCR → 文案 → 位置，五环里任何一环断了，后面的调参都是白费。前几轮在文案正则上折腾，实际上 OCR 连字都没认出来。

3. **诊断日志要覆盖每一道门，且互不干扰**
   最初四道门共用一个冷却 key，DEFER 之后 12 秒内的 VETO 全被吞掉。改成 `ocr-candidate:$pkg:$stage` 之后，一次开屏能看到完整门序列。

4. **别用「数量对」代替「质量对」**
   `文本块=10` 看着正常，但没有一个「跳过」。数量正常不代表内容可用。

5. **一次改一个变量**
   同时改 colorSpace 和显示器 ID 那两轮，两个都没生效，也不知道是哪个的问题。

## 13.2 关于安全门设计

6. **短路要短到最小范围**
   AI 回退的短路原本连带跳过了**不依赖 AI 的原生检查**。正确做法是只跳过必须依赖 AI/OCR 的那几道门。

7. **放宽一个维度要保留另一个维度**
   位置限制放宽了，但尺寸约束和第④门的位置重合保留着，所以没变成「凡是有跳过字样的都点」。

8. **父节点升级必须限量**
   向上找可点容器是必要的，但必须限制父容器面积/宽高，否则会点到整屏 ViewGroup。

9. **精确匹配要区分语义**
   `=跳过` 是规则库的主流写法，但严格相等在「跳过 5」上完全失效。只对跳过类文案容忍倒计时，不动其它 `=`。

10. **安全门的每一次放宽都要有日志**
    所有放宽（位置、可点祖先、包含匹配、去空格、跳过签名）都配了对应的诊断日志，否则下次出问题又只能猜。

## 13.3 关于环境

11. **临时目录一律用工作区**
    `/tmp` 和 `~/.android` 都不可写，所有临时产物必须落在 workspace 下。

12. **沙箱噪音不要误判**
    `[boo] permission denied: /data is outside...` 是对单个路径逐段比对的诊断输出，不代表操作失败。

13. **遇到权限问题时先申请，别绕路**
    用户明确批评过：「你应该让我给权限吧」。`ANDROID_USER_HOME` 这类环境变量虽然能让编译通过，但绕开了标准位置。

14. **改文件前先取得同意**
    这是本机用户的硬规则。改完要如实列出改了哪些文件、哪些行。

## 13.4 关于沟通

15. **「稍微修改一下」不等于授权随便改**
    先说明改哪儿、改完长什么样，再动手。

16. **不要把「顺手多做」当贴心**
    用户多次表达过不满。做完要求的事就停，需要扩展先问。

17. **承认误判**
    用户指出「ALLOW 不等于授权点击」时，纠正自己之前的说法并给出原文依据，比维护面子重要。
